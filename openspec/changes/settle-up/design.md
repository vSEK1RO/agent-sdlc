# Design

## Context

Проект уже умеет считать балансы (`compute_balances`) и хранить деньги как `int`-копейки (ADR-0001). Пользователь из issue #2 хочет не балансы, а список переводов с минимальным числом операций; эта задача NP-трудная. Реализация уже зафиксирована коммитом `6219392`, поэтому данный design описывает принятый подход ретроспективно. Мотивация — в `proposal.md`, наблюдаемое поведение — в `specs/expense-settlement/spec.md`.

## Goals / Non-Goals

**Goals:**

- Свести задачу к проверяемому критерию `число переводов = m − k`, где `k` — максимум непересекающихся подгрупп с нулевой суммой.
- Дать гарантию минимума для реальных групп (`m ≤ 14`) и безопасный деградирующий путь для больших.
- Сохранить детерминизм результата и целочисленную арифметику копеек.
- Разделить чистое вычисление плана и CLI-обвязку, чтобы optimum проверялся оракулом в тестах.

**Non-Goals:**

- Реальные платежи, банковские API и интеграция с чатом.
- Минимальность при `m > 14` — спека явно снимает это обещание.
- Изменение модели трат или алгоритма деления копеек (issue #1 уже закрыт отдельно).

## Decisions

### 1. Критерий оптимума — максимум нулевых подгрупп

Группа из `k` участников с нулевой суммой балансов рассчитывается `k − 1` переводами. Значит, минимизация переводов эквивалента максимизации числа таких непересекающихся подгрупп. Изначальный черновик сравнивал количество групп в обратную сторону (`<` вместо `>`) и давал 5 переводов для Карелии вместо 4; явная формула в ADR-0002 устранила ошибку.

**Альтернативы:** жадное слияние крупнейшего должника и крупнейшего кредитора — быстро, но даёт 4 перевода вместо 3 на контрпримере из спеки; ILP-солвер — точен, но добавляет зависимость.

### 2. Гибрид с порогом `EXACT_LIMIT = 14`

Точный DP по подмножествам используется до 14 ненулевых участников, выше — жадный алгоритм. Замеры на случайных сбалансированных группах: `n=14` ≈ 0.3 с, `n=15` ≈ 1 с, `n=16` ≈ 3 с, `n=17` ≈ 10 с, `n=18` не уложился в бюджет. Порог выбран так, чтобы CLI оставался интерактивным. Полная таблица — в `docs/adr/0002-settle-algorithm.md`.

### 3. Детерминированный выбор плана

Участники сортируются по имени; подмножества перебираются в убывающем порядке; новый разбитель принимается только если он строго увеличивает число групп; итоговый список сортируется по `(debtor, creditor, amount)`. Это даёт одинаковый вывод при любом порядке ключей во входных данных.

### 4. Общий матчер для обоих алгоритмов

После того как разбиение известно, обе ветви используют одну и ту же процедуру погашения: должник и кредитор гасятся попарно, пока не закончится один из них. Разница лишь в порядке пар — по имени внутри группы или по убыванию суммы в жадной ветви. Это уменьшает дублирование и риск рассинхрона инвариантов.

### 5. Валидация на границе

Сумма балансов проверяется до построения плана; при ненулевой сумме выбрасывается `ValueError`, который CLI уже умеет превращать в код `2` и сообщение в stderr. Нулевые балансы отфильтровываются и не создают переводов.

## Risks / Trade-offs

- **[При `m > 14` план может быть неоптимальным]** → обещание явно ограничено спекой и ADR; тест большой группы проверяет только корректность и верхнюю границу `m − 1`.
- **[Экспоненциальный рост точного DP]** → порог 14 и замеры в ADR; при изменении типичного размера групп порог пересматривается отдельным коммитом.
- **[Две алгоритмические ветви]** → общий матчер, property-тесты с оракулом для малых групп и отдельный тест для большой группы.
- **[Тесты правились после red]** → только стилистические правки ради `ruff`, зафиксированы в теле green-коммита и журнале.

## Migration Plan

Изменение ретроспективное: миграции данных нет. План — добавить OpenSpec-артефакты к уже работающему коду, прогнать `openspec validate` и оставить коммиты в истории. Откат — откат коммитов `b800481..6219392` и журнального коммита; конфигурация OpenSpec удаляется отдельно.
