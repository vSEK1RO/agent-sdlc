# Практика курса «Агентно-ориентированный SDLC»

Вы — новый разработчик в маленьком open-source проекте **«Скинемся»**: CLI для деления
общих трат в поездке, общаге, на подарок. Проект уже умеет считать балансы. За четыре пары
вы с агентом доведёте до мержа фичу, о которой просят пользователи:
**план расчёта — кто кому сколько переводит, минимальным числом переводов**
([issue #2](docs/issues/002-settle-up.md)).

По дороге выяснится, что:
- 1000 ₽ на троих поровну не делятся, и это баг ([issue #1](docs/issues/001-lost-kopeck.md));
- минимизация числа переводов — NP-трудная задача, а очевидный жадный алгоритм иногда ошибается;
- агент очень уверенно говорит «оптимально», когда это не так.

В конце у вас будет утилита, которой реально можно пользоваться после поездки с друзьями,
и — главное — история git, по которой видно, **как** вы работали с агентом.

---

## Что нужно

- Python 3.11+ и git, аккаунт на GitHub (или GitLab — тогда CI перенесите сами).
- **Любой кодинговый агент**, который читает/правит файлы и запускает команды:
  Claude Code, Codex CLI, Cursor (agent mode), Gemini CLI, Qwen Code, OpenCode / Aider / Cline
  с любой моделью, GigaCode, SourceCraft Code Assistant — что вам доступно.
- Если у агента нет сабагентов и хуков — не страшно: где нужно, в задании есть замена.

**Язык.** Стартовый проект — на Python. Хотите Go или TypeScript — пожалуйста, но сначала
портируйте стартовый проект с агентом (README + тесты — ваша спецификация; это отличное
упражнение) и укажите это в журнале. Требования к артефактам те же.

**Команды или соло.** Можно в одиночку или парами. В паре — один репозиторий,
коммиты от обоих, в журнале указывайте, кто что делал.

---

## Правила игры (их проверяют)

1. **История git — доказательство процесса.** Проверяется не только результат, но и порядок:
   спека раньше тестов, тесты (red-коммит) раньше реализации (green-коммит).
   Не переписывайте историю `rebase`/`squash` ветки `feature/settle` до мержа.
2. **Журнал** `docs/JOURNAL.md` — минимум одна запись на пару. Самое ценное — честные
   истории о том, где агент ошибся и что вы изменили, чтобы это не повторилось.
3. **Решения принимает человек.** Агент может предлагать варианты, задавать вопросы, писать
   черновики. Но если на защите вы не можете объяснить решение в своей спеке или ADR — оно не ваше.
4. **Не ищите готовое решение задачи в интернете целиком.** Задача известная (LeetCode 465),
   но смысл практики — в процессе, а не в алгоритме.

## Этап 0 · После пары 1 (дома, ~40 минут)

**Цель:** получить «базовую линию» — как вы работаете с агентом без всякого процесса.

1. Создайте свой репозиторий из шаблона, установите и запустите тесты:
   ```bash
   python -m venv .venv && source .venv/bin/activate
   pip install -e ".[dev]"
   pytest
   ```
2. Попросите агента объяснить архитектуру проекта. Сохраните ответ в журнал (кратко).
3. Исправьте [issue #1](docs/issues/001-lost-kopeck.md) с агентом — **так, как вы обычно работаете**.
   Без подготовки и специальных техник: просто «почини issue #1».
4. Запись в журнал: что попросили, что сделал агент, **кому досталась лишняя копейка и почему именно ему**.
   Были ли добавлены тесты? Прочитал ли агент `docs/adr/0001-money-in-kopecks.md`?

**Артефакты:** коммит с фиксом issue #1, запись в `docs/JOURNAL.md`.

## Этап 1 · Пара 2: спецификация и контекст

### 1.1. AGENTS.md (10 мин)

Попросите агента изучить репозиторий и предложить `AGENTS.md`. Затем отредактируйте сами.

Требования:
- не длиннее **60 строк**;
- точные команды (тесты, один тест, линтер, запуск) — проверьте, что они работают при копировании;
- карта модулей: одна строка на файл;
- правила проекта с номерами, в том числе: деньги — `int`-копейки (ADR-0001);
  логика не в `cli.py`; **«если спека молчит — не выдумывай, спроси»**;
- Definition of Done;
- никаких общих слов вроде «пиши чистый код».

Если у вас Claude Code — создайте `CLAUDE.md` с одной строкой `@AGENTS.md`.

### 1.2. Спецификация через интервью (15 мин)

1. Промпт-интервью:
   ```
   Прочитай docs/issues/002-settle-up.md и код в src/.
   Я хочу написать спецификацию по шаблону docs/specs/TEMPLATE.md.
   Не пиши спеку сразу. Задавай мне вопросы — по одному за раз,
   начиная с самых важных, — пока не сможешь написать спеку
   без единого допущения. Если вопрос касается выбора с компромиссами,
   предложи 2–3 варианта с плюсами и минусами.
   ```
2. Затем: «Напиши спеку по шаблону. Каждое решение, которое ты принял сам, а не я,
   пометь `[ДОПУЩЕНИЕ]`».
3. **Ворота 🧑‍⚖️:** пройдите по каждой пометке — примите, измените или вынесите в открытые вопросы.
   В итоговой спеке пометок нет.

Требования к `docs/specs/settle-up.md`:
- раздел «Не-цели» (минимум 3 пункта);
- минимум **3 сценария с конкретными числами**, один из них — на данных `examples/karelia.json`;
- минимум **3 инварианта** (утверждения, верные для любых входов);
- таблица граничных случаев;
- интерфейс: сигнатура функции и формат вывода CLI.

Закоммитьте спеку в `main` отдельным коммитом: `docs(spec): settle-up`.

### 1.3. Spike: агент реализует по спеке (15 мин, можно доделать дома)

```bash
git switch -c spike/settle
```
```
Прочитай AGENTS.md и docs/specs/settle-up.md.
Сначала составь план и покажи мне, не пиши код.
[после одобрения] Реализуй по плану. В конце перечисли все решения,
которые ты принял сам, потому что спека о них молчала.
```
Запустите `skinemsya --file examples/karelia.json settle`. Сколько переводов?

**Spike-ветку не мержим.** Её задача — найти дыры в спеке.

### Домашка после пары 2

- Закройте в спеке пробелы, которые выявил спайк (коммит в `main`).
- Запись в журнал: какие решения агент принял сам; что из AGENTS.md он проигнорировал.

**Артефакты этапа:** `AGENTS.md`, `docs/specs/settle-up.md`, ветка `spike/settle`, запись в журнале.

## Этап 2 · Пара 3: TDD и ADR

```bash
git switch main && git switch -c feature/settle
```

### 2.1. Тесты из спеки — red (15 мин)

Откройте **новую сессию** агента (в контексте не должно быть спайка).

```
Ты пишешь ТОЛЬКО тесты, реализации ещё нет — не создавай её.
Источник — docs/specs/settle-up.md. Для каждого сценария из «Поведения» —
пример-тест с числами из спеки. Для каждого инварианта — property-тест
на Hypothesis. Добавь оракул: полный перебор для групп ≤ 7 человек.
Запусти pytest и покажи, что тесты падают по правильной причине.
```

**Ворота 🧑‍⚖️ — прочитайте тесты:**
- [ ] ожидаемые значения взяты из спеки или посчитаны оракулом, **не** реализацией;
- [ ] нет тестов «ни о чём» (`is not None`) и тестов моков;
- [ ] в генераторе Hypothesis есть **маленькие** суммы (например, от −6 до 6) —
      иначе подгрупп с нулевой суммой почти не будет и тест оптимальности ничего не найдёт;
- [ ] тесты падают из-за отсутствия `settle`, а не из-за ошибки в самом тесте.

```bash
git commit -m "test(settle): red — tests from spec"
```

**Заморозьте тесты.**
- Claude Code: создайте `.claude/settings.json` (см. ниже) и `touch .claude/tests.lock`.
- Другой агент: правило в AGENTS.md + промпт «тесты не меняй». Финальная проверка всё равно будет в CI.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          { "type": "command", "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/protect_tests.py\"" }
        ]
      }
    ]
  }
}
```

### 2.2. ADR-0002: какой алгоритм (10 мин)

```
Подготовь черновик docs/adr/0002-settle-algorithm.md по шаблону docs/adr/TEMPLATE.md.
Варианты: жадный, точный (ДП по подмножествам), гибрид, ILP-солвер.
Для точного — замерь время на случайных группах n = 10..20 и приложи таблицу.
Раздел «Решение» оставь пустым — его пишу я.
```

Раздел **«Решение» пишете вы**. Любой вариант допустим, если:
- обоснован реальными сценариями использования (какие бывают группы?);
- последствия записаны честно, с минусами;
- есть пункт «когда пересмотреть».

Если решение меняет поведение (например, «минимум переводов при n ≤ X»), обновите спеку
и, при необходимости, тесты — **отдельным** коммитом `test(settle): red — …` до реализации.

```bash
git commit -m "docs(adr): 0002 settle algorithm"
```

### 2.3. Реализация — green, затем refactor (15 мин)

```
Реализуй settle по docs/specs/settle-up.md и docs/adr/0002-settle-algorithm.md.
Тесты в tests/ НЕ меняй. Если тест кажется неверным — остановись и объясни,
какой пункт спеки он нарушает. Работай маленькими шагами, после каждого — pytest -q.
```

Если агент считает тест неверным и он прав: спека → тест (новый red-коммит) → код.

```bash
git commit -m "feat(settle): green — ..."
```

Опционально (бонус): мутационное тестирование.
```bash
pip install mutmut
mutmut run --paths-to-mutate src/skinemsya/settle.py   # синтаксис зависит от версии mutmut — см. mutmut --help
```

### Домашка после пары 3

- Ветка `feature/settle` зелёная (`pytest`, `ruff check .`).
- Откройте PR в `main`, **не мержите**.
- Запись в журнал: пытался ли агент менять тесты; какой тест поймал неоптимальность жадного алгоритма (если поймал).

**Артефакты этапа:** red-коммит → ADR → green-коммит в истории, `tests/test_settle.py`,
`docs/adr/0002-*.md`, `src/skinemsya/settle.py`, команда `skinemsya settle`.

## Этап 3 · Пара 4: роли, ревью, мерж

### 3.1. Роли (10 мин)

Создайте минимум **reviewer** и **tester**, желательно ещё **planner** и **coder**:
- Claude Code: `.claude/agents/<роль>.md` (frontmatter `name`, `description`, `tools`);
- OpenCode: агенты в `.opencode/agent/`;
- остальные: `docs/roles/<роль>.md` — промпт роли; каждую роль запускайте в **новой сессии**.

Чек-лист ревьюера:
- [ ] только чтение (нет прав на правку кода);
- [ ] читает спеку, Accepted ADR и AGENTS.md;
- [ ] отчёт — таблица: `# | серьёзность | файл:строка | проблема | сценарий падения`;
- [ ] у каждого замечания — конкретный сценарий падения, иначе замечания нет;
- [ ] не более 5 замечаний, по убыванию серьёзности; стиль не комментирует;
- [ ] вердикт `APPROVE` / `REQUEST CHANGES`; «если замечаний нет — не выдумывай».

### 3.2. Ревью и триаж (15 мин)

1. Ревьюер в отдельном контексте пишет `docs/reviews/settle.md`. Код не правит.
2. **Ворота 🧑‍⚖️:** вы размечаете каждое замечание в том же файле:
   ✅ принято / ❌ отклонено (причина одной строкой) / 📝 не в этом PR (заведите issue).
3. Coder исправляет только ✅. Ревьюер проверяет снова. **Максимум 3 итерации.**
4. Посчитайте **точность ревьюера** = принятые / все замечания. Запишите в журнал.

### 3.3. PR → CI → merge (10 мин)

1. Добавьте в `.github/workflows/ci.yml` шаг (нужна полная история git):
   ```yaml
         - uses: actions/checkout@v4
           with:
             fetch-depth: 0
         # ...
         - name: Tests untouched after red commit
           if: github.event_name == 'pull_request'
           run: scripts/check_tests_untouched.sh origin/${{ github.base_ref }}
   ```
2. Заполните описание PR по шаблону: ссылки на спеку, ADR, отчёт ревью,
   раздел «Что агент сделал не так и как это поймали».
3. CI зелёный → merge (merge commit, без squash — история нужна для проверки).

### 3.4. Бонус: мини-фича через полный пайплайн

[Issue #3](docs/issues/003-chat-format.md) — вывод для чата.
Пройдите **весь** путь, по коммиту на шаг: короткая спека → planner → tester (red) → coder (green)
→ reviewer → PR. Это лучший способ почувствовать, где пайплайн помогает, а где избыточен,
— и это отличный материал для защиты.

## FAQ

**Агент сразу написал оптимальный алгоритм. Это плохо?**
Нет. Но покажите тестом, что он оптимален (оракул), и опишите выбор в ADR так же, как если бы выбирали сами.

**Можно выбрать жадный алгоритм?**
Да, если это ваше осознанное решение с записанными последствиями. Тогда спека не должна обещать «минимум».

**Агент без хуков и сабагентов — я проиграл?**
Нет. Хук заменяется правилом + CI-проверкой, сабагент — новой сессией с промптом роли из `docs/roles/`.
Механизм вторичен, принцип (чистый контекст, минимальные права, артефакт на выходе) — нет.

**Сколько токенов это стоит?**
Немного: проект маленький. Самое дорогое — бесконечные циклы «исправь → проверь».
Ограничивайте итерации и начинайте новую сессию, когда контекст замусорился.

**Мой агент удалил/сломал что-то важное.**
Поздравляю — это отличная запись в журнал. Откатитесь через git и запишите, какое право или
проверка это предотвратили бы.
