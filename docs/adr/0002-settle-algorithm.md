# ADR-0002. Гибрид: точный DP до 14 участников, жадный алгоритм выше

- **Статус:** Accepted
- **Дата:** 2026-11-27
- **Авторы:** пользователь (решение), OpenCode (черновик и замеры)
- **Связано:** спека `docs/specs/settle-up.md`, issue `docs/issues/002-settle-up.md`

## Контекст

Issue #2 просит показать «кто кому сколько переводит» и явно говорит: «чем меньше переводов — тем лучше». В `ASSIGNMENT.md` отмечено, что минимизация числа переводов — NP-трудная задача и что жадный алгоритм иногда ошибается. Нужно выбрать алгоритм, который даёт настоящий минимум для реальных поездок, но не превращает CLI в долго считающий калькулятор на больших группах.

Реальные данные проекта: `examples/karelia.json` — 6 участников, 6 ненулевых балансов. Типичная группа после поездки — от 2 до 10 человек. При этом интерфейс консольный: пользователь ждёт ответа сразу, а не минуту.

Обозначим `m` — число участников с ненулевым балансом. Каждый перевод гасит одного должника и одного кредитора; план с `k` непересекающимися подгруппами с нулевой суммой требует `m − k` переводов. Значит, минимум переводов равен минимуму при максимальном `k`.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только жадный (жадкий debtor↔creditor) | O(m log m), мгновенно, одна ветка кода | Не гарантирует минимум; контрпример из спеки 4.3: 4 перевода вместо 3. Спека тогда не должна обещать «минимум» |
| B. Только точный DP по подмножествам | Гарантирует минимум для любого `m` | Экспоненциальный рост: на `m = 17` один прогон ~9–12 с, `m = 18` не уложился в 120-секундный бюджет замера |
| C. Гибрид: точный DP при `m ≤ 14`, жадный при `m > 14` | Минимум для реальных групп; CLI не зависает; поведение явно описано в спеке | Два алгоритма и порог в спеке/коде; выше порога минимум не обещан |
| D. ILP-солвер | Точность на больших группах | Новая внешняя зависимость, сборка сложнее, избыточно для 6–10 человек |

### Замеры точного DP

Случайные сбалансированные группы из целых копеек в диапазоне −9…9, по 2 прогона на каждый `m`, Python 3.13:

| `m` | Минимум, с | Максимум, с |
|---:|---:|---:|
| 10 | 0.003 | 0.003 |
| 11 | 0.010 | 0.012 |
| 12 | 0.031 | 0.036 |
| 13 | 0.111 | 0.123 |
| 14 | 0.280 | 0.353 |
| 15 | 1.024 | 1.060 |
| 16 | 2.883 | 2.996 |
| 17 | 9.161 | 12.060 |
| 18 | не уложился в бюджет замера | — |

Порог выбран на 14: наихудший замер ~0.35 с — приемлемо для CLI; на 15 уже больше секунды, на 17 — очень дорого.

## Решение

Принят **вариант C**. Точный DP по подмножествам используется при `m ≤ 14` (`EXACT_LIMIT = 14`); он перебирает разбиения на подгруппы с нулевой суммой и максимизирует их число, значит даёт минимальное число переводов. При `m > 14` используется жадное согласование должника и кредитора с наибольшими суммами: план остаётся корректным и содержит не более `m − 1` переводов, но минимальность не гарантируется.

Это решение осознанно сужает обещание из issue #2: «минимум» обещан только для `m ≤ 14`, и спека `settle-up.md` говорит об этом прямо. Контрпример из сценария 4.3 показывает, почему жадный алгоритм не может быть единственным вариантом.

## Последствия

- (+) Для Карелии и любых обычных поездок (`m ≤ 14`) пользователь получает гарантированно минимальный план: 4 перевода вместо 11 в исторической задаче Гоши.
- (+) CLI остаётся быстрым на любом размере группы.
- (+) Поведение детерминировано и проверяется оракулом полного перебора в тестах.
- (−) При `m > 14` результат может быть неоптимальным; нужно помнить об этом в документации и не обещать «минимум» без оговорок.
- (−) Два алгоритма и один магический порог: спека, код и ADR должны синхронно обновляться при изменении `EXACT_LIMIT`.
- (−) Точный DP хранит массивы размера `2^m`; при `m = 14` это ~16 К записей.

**Когда пересмотреть:** если типичные группы в проекте станут больше 14 человек; если появится алгоритм без внешних зависимостей с лучшей асимптотикой; если требования к отклику CLI ужесточатся; если сценарии с `m > 14` потребуют гарантированного минимума — тогда вернуться к варианту D.
