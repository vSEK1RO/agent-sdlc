# Спецификация: план расчёта (`settle`)

- **Статус:** Approved
- **Issue:** docs/issues/002-settle-up.md
- **Связанные ADR:** docs/adr/0002-settle-algorithm.md

## 1. Зачем (контекст и проблема)

Гоша вернулся из поездки: команда `balance` показывает, кто в плюсе, а кто в минусе, но не отвечает на главный вопрос — «кому мне переводить?». В прошлый раз друзья считали в Excel, получилось 11 переводов, все путались, а Дима перевёл дважды. Нужна одна команда, которая печатает готовый список переводов и по возможности укладывается в минимальное их число: никто не хочет скидывать по 37 рублей пяти разным людям.

## 2. Цели

- По балансам группы построить список переводов вида «кто → кому → сколько».
- Гарантировать **минимальное число переводов**, если число участников с ненулевым балансом `m ≤ 14`.
- Для `m > 14` вернуть корректный план не более чем из `m − 1` переводов, не падая и не обещая минимума.
- Сделать результат детерминированным: один и тот же ввод даёт один и тот же список.
- Вывести план в консоль в виде, который удобно скопировать в общий чат.

## 3. Не-цели (что мы сознательно НЕ делаем)

- Не инициируем реальные платежи и не интегрируемся с банками — только печать инструкции для людей.
- Не минимизируем сумму переводов или число получателей: сумма полностью определяется балансами.
- Не объясняем, из-за каких именно трат возник долг: на выходе только итоговый план.
- Не делаем формат для чата (markdown/Telegram) — это отдельный [issue #3](docs/issues/003-chat-format.md).
- Не поддерживаем разбалансированные данные: если сумма балансов не нуль, это ошибка ввода, а не повод «додавить» копейку.

## 4. Поведение

Все суммы ниже — копейки; в скобках для читаемости указаны рубли.

### Сценарий 4.1. Двое, один перевод

- Дано: `{"Аня": 50_000, "Боря": -50_000}` (Аня +500 ₽, Боря −500 ₽).
- Когда: вызван `settle_balances`.
- Тогда: ровно один перевод `Боря → Аня 500.00 ₽` (`Transfer(debtor="Боря", creditor="Аня", amount=50_000)`).

### Сценарий 4.2. Трое, обычная трата

- Дано: группа Аня, Боря, Вика; Аня заплатила 900 ₽ за всех. Балансы: Аня `+60_000`, Боря `−30_000`, Вика `−30_000`.
- Когда: вызван `settle(group)`.
- Тогда: два перевода — `Боря → Аня 300.00 ₽`, `Вика → Аня 300.00 ₽`.

### Сценарий 4.3. Жадный алгоритм ошибается

- Дано: балансы Аня `+60_000`, Боря `+40_000`, Вика `−40_000`, Гоша `−40_000`, Дима `−20_000`.
- Когда: вызван `settle_balances`.
- Тогда: минимальное число переводов — **3**, а не 4, которые даёт жадное слияние самых крупных должника и кредитора:
  - `Вика → Боря 400.00 ₽`
  - `Гоша → Аня 400.00 ₽`
  - `Дима → Аня 200.00 ₽`

### Сценарий 4.4. Карелия (`examples/karelia.json`)

- Дано: балансы Аня `+700_000`, Боря `+200_000`, Вика `+200_000`, Гоша `−400_000`, Дима `−400_000`, Егор `−300_000`.
- Когда: выполнена команда `skinemsya --file examples/karelia.json settle`.
- Тогда: **4 перевода** (минимум для этих шести участников):
  - `Гоша → Боря 2 000.00 ₽`
  - `Гоша → Вика 2 000.00 ₽`
  - `Дима → Аня 4 000.00 ₽`
  - `Егор → Аня 3 000.00 ₽`

## 5. Интерфейс

- `Transfer` — неизменяемый dataclass: `debtor: str`, `creditor: str`, `amount: int`. `amount` — целые копейки, всегда `> 0`.
- `settle_balances(balances: Mapping[str, int]) -> list[Transfer]` — чистая функция, главная точка входа для тестов.
- `settle(group: Group) -> list[Transfer]` — обёртка: `settle_balances(compute_balances(group))`.
- CLI: `skinemsya [--file PATH] settle`:
  - на каждый перевод печатает строку `{debtor} → {creditor}  {format_rub(amount)}`;
  - если переводов нет, печатает `Переводы не нужны.`;
  - возвращает `0` при успехе и `2` с сообщением `Ошибка: ...` в stderr при неверных данных.
- Порядок строк детерминирован: сортировка по `(debtor, creditor, amount)`.
- Порог `EXACT_LIMIT = 14`: точный перебор используется при `m ≤ 14` участниках с ненулевым балансом; выше — жадный алгоритм.

## 6. Инварианты

- Сумма всех балансов равна нулю; иначе `settle_balances` бросает `ValueError`.
- Для каждого перевода: `balances[debtor] < 0`, `balances[creditor] > 0`, `amount > 0`, `debtor != creditor`.
- После применения всех переводов чистый результат каждого участника равен его балансу: `получено − отдано == balances[имя]`.
- Число переводов равно `m − k`, где `k` — максимум непересекающихся подгрупп с нулевой суммой; при `m ≤ 14` это глобальный минимум (проверяется оракулом полного перебора).
- При `m > 14` число переводов `≤ m − 1`; минимальность **не гарантируется** и нигде не обещается.
- Нулевые балансы не порождают переводов; пустые переводы (`amount == 0`) не создаются никогда.

## 7. Граничные случаи и ошибки

| Ситуация | Ожидаемое поведение |
|---|---|
| Пустая группа или все балансы нулевые | `[]`; CLI печатает `Переводы не нужны.` |
| Сумма балансов не равна нулю | `ValueError`; CLI возвращает `2` и пишет `Ошибка: ...` в stderr |
| Участник с нулевым балансом среди ненулевых | В плане не участвует |
| `m = 14` | Точный минимум, время работы ≈ 0.3–0.4 с на обычном ноутбуке |
| `m ≥ 15` | Жадный план `≤ m − 1`, без падения; минимум не обещан |
| Балансы в копейках, включая 1 копейку | Суммируются как `int`, без округлений и плавающих точек |

## 9. Открытые вопросы

- Порог `EXACT_LIMIT` пересматривается по замерам в ADR-0002; если типичные группы станут больше 14 человек, Spec и ADR обновляются отдельными коммитами.
